Digest trees over indexes

How two durable nodes can learn whether their stores hold the same entities, and find exactly the ones that differ, by comparing digests kept in a tree over each index.

Written 2026-10-03 from 60-index-tree-study.html (the tree and its protocols), section 4 of 61-holder-discovery-study.html (residency claims) and section 5 of 62-share-predicate-study.html (shares as prefixes), in the lexicon of the storage engine contract branch.

Historical proposal. See the current standalone contract before using this page as implementation guidance. Daniel has not ruled on this mechanism and none of it is built. Every mechanism on this page is a proposal, and choices still open are marked open. Figures marked computed come from the studies’ cost arithmetic and figures marked simulated from their Python simulations; none was measured on an ankurah store.

1The problem

Two durable nodes each hold a store of entities. Every entity has a head, the set of its newest event ids, and because each event id is a hash over the ids of its parents, the head commits to the entity’s entire history. When the two connect, they need to learn cheaply whether they hold the same entities at the same heads, and if not, which entities differ. They need this after any length of separation, from seconds to months, whether or not they have met before, and at any store size from a few thousand entities to fifty million. Two common shortcuts are ruled out. Events carry no monotonic ids, so there is no sequence number or vector of per-replica counters to compare, and no central registry records which store holds what.

2The idea

A store already orders its entities by keys to serve lookups and queries: by entity id, by the value of a property, by component membership. The proposal builds a tree over such an index. Its leaves are the entities in key order, and every tree node above them summarizes the leaves beneath it with a digest that can be added to and subtracted from, so that equal digests mean equal sets of leaves. Two durable nodes compare the roots of their trees. Where the digests differ they compare the digests of the children, and they keep descending only into children that differ until they reach leaves, which name the entities that differ. For each of those entities the two durable nodes exchange the events each lacks, and the event DAG merges them as it does today. A predicate over an indexed property selects a set of branches of that property’s tree, so a partial replica, or a share that one durable node grants another, compares only the branches it keeps.

The program’s reconciliation design, 11-reconciliation-cost.md, calls these two parts level one and level two. The tree replaces only the first part; the exchange of events stays as that design defines it.

3The structure

The figures use a store of eight entities, which section 4 follows through a whole session.

Leaves

A store keeps one leaf per entity in each hashed index, the indexes chosen to carry a tree; every store hashes its primary index, which orders entities by id. A leaf’s key is the entity’s key in that index: in the primary index the entity id, the 32-byte id of its genesis event, and in a property index the canonical byte encoding of the property’s value followed by the entity id, so that equal values still give distinct keys. The leaf’s item is the entity id with the entity’s head, its event ids sorted, and the leaf’s digest is a hash of that item mapped to a point on an elliptic curve. The store keeps each leaf as a folded row holding the key, the head, the leaf digest and the commit position at which the tree last took it in, which is how the store still knows the old digest and key to subtract after the head changes. Whether the leaf should be the head, as proposed, or a digest of every event id the store holds for the entity is open.

Tree nodes

A tree node is a hexadecimal key prefix. The root is the empty prefix, its sixteen children are the prefixes 0 to f, theirs are 00 to ff, and so on down. A tree node carries three values folded over the leaves whose keys begin with its prefix: the digest, which is the sum of their leaf digests in the curve group; their count; and the commit position, the highest position in this store’s commit log at which any of them last changed. Each value equals the same fold over the sixteen children. The digest and the count describe content and can be compared across stores. The commit position orders one store’s own commits and means something only to a partner that keeps a cursor into that store. A store keeps rows only down to the depth at which a prefix holds no more than a bucket of leaves (about sixty-four, by the proposed default) and answers for any deeper prefix by scanning the folded rows in its range.

Derived, never authored

Tree nodes are derived state. A store computes them from its own leaves and could drop and rebuild every one of them from the folded rows without losing anything. No event creates or changes a tree node, tree nodes have no history, and nothing about them enters the event DAG. A tree node’s name is its index’s identity followed by its prefix, so durable nodes that have never met name a branch the same way, and if they hold the same leaves under it they hold the same digest for it. Ids drawn for tree nodes would give two stores two names for one range, and tree nodes made into entities would add an event to the DAG for every index change, as unbase’s index did (03-unbase-lessons.md, the replicated root index).

Why the digest is additive

Because a tree node’s digest is a sum of leaf digests, three things follow.

  • Each change to an entity’s head updates one row per level. The refresher subtracts the old leaf digest and adds the new one at each tree node on the entity’s path, and reads no sibling.
  • The digest of any key range is the sum of the digests of the aligned prefixes that tile it, so a range predicate, or the overlap of two durable nodes’ interests, has an exact digest without a tree of its own.
  • A prefix’s digest depends only on the leaves under it, not on the rows a store keeps, its bucket size or the order in which its entities arrived. Each store keeps rows only for the depths worth keeping at its size, and stores that chose differently still agree on every digest.

Why an elliptic curve, and what a Merkle tree would cost

A plain sum of hashes, or their XOR, would be just as additive, but authors choose their events and therefore the hashes in the sum, which lets Wagner’s generalized birthday attack find crafted items with any chosen sum in about two to the thirty-second steps for a 256-bit modular sum (XOR yields to linear algebra in seconds), while in a prime-order elliptic-curve group the same search is as hard as computing a discrete logarithm.

The proposal is an elliptic-curve multiset hash on a 256-bit curve (Maitin-Shepard, Tibouchi and Aranha, 2017). A digest is 33 bytes with about 128 bits of collision resistance, removing a leaf is a subtraction, and each changed leaf costs one hash-to-curve, about 11 to 14 microseconds on secp256k1 by published benchmarks (a literature figure, cited in 60-index-tree-study.html section 1, the structure stated precisely). The price is a cryptographic dependency that ankurah does not have today. The choice of digest is open.

The alternative, a Merkle tree whose tree nodes hash their sixteen children’s digests, needs no curve library but costs in three places. Each commit must read all sixteen children of every tree node on its path, or keep them inline in every row, which the study computes at 2.1 to 4.3 KB of writes per commit per hashed index against 156 to 312 bytes for the additive digest (computed, 60-index-tree-study.html section 3, maintenance cost per commit per index). The digest commits to the tree’s shape, so every durable node must keep the same fanout and bucket size forever. And a key range that is not one whole subtree has no digest, so range predicates and overlapping interests lose theirs. The studies keep the Merkle tree as the fallback.

The refresher

A commit does not touch the tree. It writes one extra row, in the store’s commit log: the commit position, the event id, the entity id and a digest chained from the previous row, as 11-reconciliation-cost.md specifies. A head change that stores no new event writes a log row of its own. One refresher per store reads the log after the position it last folded, groups the rows by entity, and reads each touched entity’s head and folded row. It subtracts the old leaf digest along the old key’s path and adds the new one along the new key’s path, writes each changed row once per batch, and records on the root, in the same transaction, the position it has folded through.

Two rules keep it safe. It advances only by a compare-and-set on the root’s commit position, because two refreshers folding the same stretch of log would add every change twice without any error. And it never folds past the store’s recovery checkpoint, the position below which every stored event is reflected in a saved head, so a crash cannot leave the tree ahead of the heads. Each session starts with a refresh, which costs the commits since the last one.

Updating the tree inside each commit would also work, but the studies propose the refresher on every engine: it batches writes, and on PostgreSQL with concurrent writers every in-commit update would hold the root row until commit and serialize commits that run side by side today. The commit log stays either way, for crash recovery and for durable nodes sharing one store, and the tree never replaces it. That arrangement is open.

The size rule

Below about a hundred thousand entities a store keeps no tree to descend, only its root row and perhaps a level or two for claims, and finds differences with a per-session encode over all its entities (described after the example). Between a hundred thousand and a million entities it keeps rows down to branches of about a thousand leaves and finishes each differing branch with the encode. From a million the full tree starts to pay, and from ten million it wins every small session at every link latency; at fifty million an encode would scan the store for about 41 seconds per session per link, so it survives only to finish a differing bucket or a session in which much of the store differs. These boundaries are computed and await measurement (60-index-tree-study.html section 10, the recommendation).

4A minimal example

Two stores, two commits

Alice and Bob each run a durable node, and last week they synced, so both stores hold the same eight entities at the same heads. Ids here are shortened to four hexadecimal digits. The entities fall under the prefixes 3 and b, then 3a, 3d, b2 and b9, so the tree has two levels below the root. A real store would give no row to a prefix of two leaves; the example keeps one for every prefix so that there is something to descend.

While they are apart, Bob marks task 3d5b… done: his node stores event 8d3e…, whose parent is 2b61…, and the task’s head on Bob’s store becomes {8d3e…}. Alice edits note b244… the same day: her node stores event f172…, whose parent is 9f4d…, and the note’s head on Alice’s store becomes {f172…}. Neither knows of the other’s change.

The session

  1. Each refresher folds its own commit. Bob’s refresher takes the old leaf digest of 3d5b… from its folded row, computes the new one from {8d3e…}, and applies the difference to 3d, 3 and the root; Alice’s does the same for b244… on b2, b and the root. Each side rewrites one folded row and three tree-node rows and reads nothing else.
  2. They connect and exchange roots at full width: the 33-byte digest, the count 8 and the folded commit position, about 100 bytes each way, with random bytes toward a salt for the session. The digests differ. The counts agree, so both hold eight entities and something about them differs.
  3. Alice sends the root’s sixteen child summaries, each a 4-byte count and the first 8 bytes of the child’s digest hashed with the session salt: 192 bytes. Bob finds that 3 and b differ; the fourteen empty prefixes agree.
  4. Bob sends the sixteen child summaries of 3 and of b, 384 bytes. Alice finds that 3d and b2 differ. Each message goes one level down, so a round trip covers two levels.
  5. Alice sends her leaves under 3d and b2, entity id and head, about 64 bytes each, with each prefix’s full-width digest: about 320 bytes. Bob checks that the leaves add up to the digests, which exposes a forged or garbled list, and compares heads. 3d5b… and b244… differ; the other two match.
  6. Bob sends his two heads, the event 8d3e… and a request for f172…, about 500 bytes. He sends 8d3e… unasked because Alice’s head for 3d5b…, {2b61…}, is its parent, and he asks for f172… because Alice’s head for b244… names an event he lacks. When heads are further apart, each side also sends a Bloom filter of its recent events so that the other can tell which ancestors to send, as the per-entity exchange in 11-reconciliation-cost.md defines.
  7. Alice sends f172…, about 300 bytes.
  8. Each applies, refreshes and checks. Each side applies the event it received through the event DAG, as ankurah does today: the event’s parent is present, so the entity’s head advances. Each refresher folds the new log row, and the roots, exchanged again at full width, are equal.

In all, about 2 KB crossed the link in three and a half round trips, and each side read a handful of rows. At fifty million entities the tree is five levels deep instead of two, and a session descends the same way through more levels.

When the two kept cursors

Descent by digest needs no memory of earlier sessions, so it serves first meetings and long absences alike. A durable node that kept a cursor from its last session with a partner (the partner’s commit position then, and enough to detect that the partner’s log was reset) can instead ask for what changed since. The partner walks only the tree nodes whose commit position is newer than the cursor and streams the leaves beneath them in one round trip. The full-width root check still closes the session, and a mismatch falls back to descent by digest.

First contact with an empty store

Now suppose Bob has just joined and his store holds nothing.

  1. They exchange roots, about 100 bytes each way. Alice’s count is 8 and Bob’s is 0.
  2. Alice sends the leaf list for the whole root, about 520 bytes. Bob hashes each leaf to the curve and adds the points; the sum equals Alice’s root digest, so the list is exactly the set that digest names, with nothing missing or invented.
  3. Bob asks for the events of all eight entities, sending an empty head for each, about 300 bytes.
  4. Alice sends every event of the eight, oldest first so that each event’s parents arrive before it: about 12 KB if the eight hold forty events of 300 bytes. Bob applies them and his refresher folds eight new leaves.
  5. The roots, exchanged again at full width, are equal.

At real sizes the leaf list arrives in pages, each checked against the digests of the prefixes it covers, and the tree costs an empty joiner about 64 bytes per entity beyond the events themselves. The same rule serves any branch that one side lacks or barely holds: when the counts show that a descent would cost more than the list, the side holding the branch sends its leaves.

Small stores and the per-session encode

In stores below about a hundred thousand entities, two durable nodes reconcile with a per-session encode instead of a descent. Each side reads its pairs of entity id and head, and the two run one rateless set-reconciliation code over them (rateless invertible Bloom lookup tables, as 11-reconciliation-cost.md specifies), keyed afresh from randomness both sides contribute so that no one can prepare colliding items. Rateless means the encoder fixes no size in advance: it streams coded symbols, each combining a pseudo-random subset of the items, until the receiver has decoded every item that differs, so the bytes sent follow the size of the difference. It costs about 240 bytes per differing entity in one round trip, after a scan of about 8 milliseconds at ten thousand entities and 0.8 seconds at a million (computed, 60-index-tree-study.html section 4, the protocols on the tree). The differing entities then take the same per-entity exchange.

5Why it is beneficial

Equal roots prove agreement between durable nodes that never met. A tree node’s digest depends only on the set of leaves beneath it, not on the order in which events arrived, the partners they came from or the rows a store keeps. The digest names the set, not the path that built it, a property called history independence. Two full replicas with equal primary roots therefore hold the same events for every entity even if they have never exchanged a message, provided the curve hash resists collisions. A commit log or a cursor, by contrast, describes one store’s history and means something only to a partner that has followed it.

The cost follows what changed, not the size of the store. A descent reads and sends about the number of differing entities times the depth of the tree, and the depth grows only with the logarithm of the store’s size. Ten differing entities in a store of fifty million cost about 15 KB and 48 row reads, where a per-session encode would scan the store for about 41 seconds (computed, 60-index-tree-study.html section 4, the protocols on the tree).

One structure serves every way of replicating.

  • A full replica compares one root, the primary index’s.
  • A partial replica compares the branches its predicate selects. Equality on an indexed property is one prefix, because the encoded value leads the key; a range is a union of aligned prefixes; membership in a component is one prefix of the membership index. Two partial replicas compare the branches both keep (60-index-tree-study.html section 5, predicates as branches).
  • A share is one prefix of one index. When every shared entity carries the shared project’s id in a property, an index keyed by that id and then the entity id holds the whole share under one prefix, whose digest a fifty-million-entity store and a peer holding only the share compute alike. A share of a few thousand entities is small enough for the per-session encode (62-share-predicate-study.html section 5, composition with the replication substrate). Membership that follows references does not sum so simply: an entity counts once per path that reaches it, so an exact digest again needs one row per shared entity keyed under the project.
  • A residency claim names a tree node at any depth. It says that a durable node holds the entities under one prefix, down to a single entity, whether it promises to hold all of them, and at what digest, count and commit position (61-holder-discovery-study.html section 4, one residency claim at every depth). A claim covers its whole subtree, so a full replica claims with one root, a partial replica with a few branches and a holder of scattered entities with leaves, and one table answers who holds an entity. That study places the duty to keep copies for durability on the primary index, where an entity’s key never moves.

Any durable node can compute any prefix’s digest from its own store, whether or not it keeps a row for that prefix. That lets an archive of fifty million entities and a laptop compare a branch both hold, lets anyone check a claimed digest against a leaf list, and keeps the digits a descent goes by independent of the rows each store keeps.

No monotonic ids, and nothing added to events. The tree uses only entity ids and event ids. Tree nodes take their names from the index and the prefix, commit positions stay local to one store, and nothing is indexed by the set of durable nodes, so forgetting a cursor or a claim costs only a longer next session.

  • A cryptographic dependency: a curve library with a standard hash-to-curve encoding.
  • A new byte-keyed table per hashed index, because SQLite, PostgreSQL and IndexedDB store entity ids as base64 text that does not sort in byte order, and one canonical byte encoding of property values in shared code.
  • A commit position that orders each store’s commits, which no engine exposes today and which the reconciliation design’s commit log needs anyway.
  • A refresh before each session, and a periodic audit that rebuilds the root from a scan to catch a tree that has drifted.

What it does not do

  • It says equal or different, never ahead or behind. The per-entity exchange compares heads through the event DAG, which tells an ancestor from a descendant or from a concurrent change.
  • It does not prove completeness. Equal digests prove that two sets are equal, not that either holds everything that exists. A branch is complete only relative to a partner that covers it, as of that partner’s commit position, after a finished reconciliation.
  • It does not read absence as deletion. A leaf missing under a prefix on one side means that the entity sits under another key there, because its indexed value changed, or is not held at all; the two settle it by entity id.
  • It does not replace the commit log, which crash recovery and durable nodes sharing one store depend on.
  • It covers only what heads cover. An event stored under no head is invisible until crash recovery integrates it, and admission evidence, which sits outside event ids, is reconciled as its own stream.
  • It does not make every predicate a set of branches. A predicate over a property that no hashed index orders is a filter, and comparing it falls back to a per-session encode over the filtered entities.
  • It does not let hearsay decide. A digest or claim relayed by a third durable node steers where to look. Only leaves checked against a digest and events checked by id change what a durable node holds or promises.

Rulings still open

  • open The digest. The additive elliptic-curve multiset digest, as proposed, or a Merkle hash over children as the fallback.
  • open The leaf. The entity’s sorted head, as proposed, or an additive digest of every event id the store holds for the entity.
  • open Which indexes are hashed. Proposed: the replication class (the policy definition that names a predicate) or the share names the index its predicate follows, the durable nodes serving it hash that index, and every store hashes the primary index.
  • open The tree beside the log. Proposed: the commit log stays as specified, the tree is folded from it, and a partner’s cursor becomes the partner’s folded commit position.
  • open Per-member facts as hearsay. Whether a durable node’s entry in the system’s roster may list the branches it promises to keep, and whether a durable node may relay the roots it has heard from others, on the ground that forgetting either is always safe.

The finer parameters, such as descending by hexadecimal digits, eight-byte salted digests during a descent and buckets of about sixty-four leaves, are proposals the studies leave to measurement.

7Glossary

Entity
An object in an ankurah store, with one identity (the id of its genesis event), a state and a set of component memberships.
Head
The set of an entity’s newest event ids. Because each event id hashes its parents’ ids, the head commits to the entity’s whole history.
Event DAG
The per-entity graph in which each event names its parents. Ankurah merges concurrent events through it; reconciliation only ships events.
Index
An ordering of a store’s entities by a key: entity id (the primary index), a property’s encoded value then entity id, or component id then entity id (a membership index). A hashed index also keeps a digest tree.
Prefix
The leading hexadecimal digits of a key. A prefix names a tree node and the range of keys beneath it.
Bucket
The leaves under the deepest prefix a store keeps a row for, read by scanning that prefix’s range of folded rows.
Folded row
One entity’s leaf in one hashed index: key, head, leaf digest and the commit position last folded.
Digest
A fixed-size value standing for a set of leaves; equal digests mean equal sets.
Additive digest
A digest updated by adding or subtracting a leaf’s digest, so that the digests of disjoint ranges sum to the digest of their union. The proposal uses an elliptic-curve multiset hash.
Refresher
The one process per store that folds the commit log into the folded rows and tree nodes, in batches.
Commit position
A commit’s place in one store’s commit log, never compared across stores. A tree node carries the highest commit position beneath it.
Descent
Comparing child digests level by level and going down only where they differ. A descent by position instead follows the commit positions newer than a cursor.
Per-session encode
A rateless set-reconciliation code built fresh for one session over pairs of entity id and head. It finds the differing pairs in about one round trip, after a scan.
Residency claim
A durable node’s statement that it holds the entities under a named tree node, with or without a promise to hold all of them, at a stated digest, count and commit position. Claims steer and never decide.
Share
The set of entities one durable node grants another, such as a project and everything filed under it.
