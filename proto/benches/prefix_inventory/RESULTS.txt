Flat prefix inventory results — 2026-10-17

Recommendation: retain the flat layout and investigate owned-buffer/borrowed
consumption first. Prefix coding is useful for repeated keys, but it is a
separate bandwidth optimization. It does not remove allocations if decoding
still materializes every owned key and Clock. A recursive representation is not
needed to obtain these savings. No production compression or ownership change
has been made; the only production change here is KnownState.regions -> spans.

What this establishes

- Most CPU/allocation improvement comes from consuming packed bytes through
  views, including the unchanged wire format. Those gains must not be credited
  to prefix compression. Clocks in timed fixtures are canonical; noncanonical
  clocks require a tested allocating normalization fallback.
- With shared keys, compression adds about 5 us to the conservative packed
  decoder while saving about 80 KB per inventory. For random keys it adds
  about 8 us for less than 2 KB saved. A universal compression threshold is
  not established; encoder cost and real consuming paths remain unmeasured.
- Prefix coding alone leaves owned allocation counts unchanged. Same-parser
  owned controls for shared keys are about 398 us plain / 401 us prefix.
  The wide-key owned result (80 us production / 30 us prefix) is mostly parser
  behavior: the same-parser plain control already takes about 31 us.
- Retaining one byte buffer avoids per-head boxes. Traversing compressed keys
  still needs one reusable full-key scratch buffer (43 bytes in the shared
  example); two passes allocate it twice sequentially. Views of that scratch
  cannot be retained after advancing, and arbitrary row access needs replay
  or additional checkpoints. This is sequential storage, not a linked heap.
- Small/ID-only inputs need a plain fallback. Encoding selection could be
  per inventory, without splitting an inventory into artificial wire pages.

Validation and limits

Exact bytes/fields and clock normalization are checked before all three runs.
The plain prototype encoder equals production bytes on all fixtures. Both
decoders reject repaired-envelope truncations, trailing data, unsupported
versions, invalid prefixes, invalid clock generations, excess row counts and
excess expanded-key work; all bound forms and duplicate clock normalization
are covered. This is not comprehensive adversarial fuzzing or hardening.

The spans rename passed proto43, core462 (one existing ignored), integration39
and JWT-auth test-target checking. Benchmark Clippy has no source warnings;
existing workspace manifest warnings remain. Earlier prototype compile/parser
check failures were corrected before measurement and preserved in private
build logs; none of those failed builds supplies a timing result.

There is no browser/network/query-readiness claim. Reading through views must
be integrated with actual comparison ownership and validation before making
an end-to-end performance claim. No protocol or API adoption is implied.
README.txt documents reproduction and modes; results.json preserves samples.
